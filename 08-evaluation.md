# 08 — Evaluation

> Goal: know whether your memory system is good, know when it regresses, and be able to read a
> benchmark claim without being fooled by it.
>
> Evaluation is the difference between a memory system that improves and one that drifts. Build the
> harness before you build the third feature.

---

## 8.1 The three-number rule

**Never report memory quality as a single number.** Always report a triple:

```
(accuracy, tokens per query, latency p95)
```

A system at 95% accuracy consuming 40k tokens per query is, for almost every production deployment,
worse than one at 89% at 5k tokens — because the first one is 8× the cost, slower, and closer to the
context-rot cliff. The published benchmark numbers that are worth anything report cost alongside
accuracy; the ones that don't are marketing.

The corollary for reading vendor claims: **pair every number with its partner.** Pair accuracy with
token cost. Pair a single-session score with a multi-session one. Pair a long-context probe with an
actual memory eval. A number without its pair is not evidence.

---

## 8.2 The public benchmarks

You should know these four, what they test, and where each falls short.

### LoCoMo (Long Conversational Memory)

Multi-session dialogues generated by a machine–human pipeline: LLM personas grounded on temporal
event graphs produce long conversations, which humans then edit for long-range consistency. Roughly
10 released dialogues, each on the order of hundreds of turns across up to ~32 sessions, with ~1,500+
annotated QA pairs spanning **single-hop, multi-hop, temporal, and open-domain** categories.

*Use it for:* a reproducible baseline; it is the most widely reported number so it lets you compare
against published systems.

*Limitations:* the contexts are modest by current standards, and it does not explicitly score
**knowledge updates** — the supersession behaviour from chapter 04 that matters most in production.
Treat LoCoMo as a floor, not a bar.

### LongMemEval

500 curated questions across six ability categories: single-session user recall, single-session
assistant recall, preference recall, **knowledge update**, temporal reasoning, and multi-session
reasoning. Ships in two sizes — `_S` with chat histories around 115k tokens over roughly 40 sessions,
and `_M` extending to hundreds of sessions per history, which is the regime where context-stuffing
stops working entirely.

Two design choices make it the more useful benchmark:

1. **Knowledge update questions** directly test whether your system handles "I moved" correctly.
   This is the single most production-relevant category in any public benchmark.
2. **Abstention questions** ask about events that never happened; the system is scored on correctly
   saying "you never told me that." **This is enormously important and almost universally ignored.**
   A memory system that confidently invents a plausible memory is worse than one with no memory.

*Limitations:* still chat-shaped; does not cover tool-using agents, procedural memory, or trajectory
memory.

### BEAM

Designed for the scale problem: evaluations at **1M and 10M token** histories, explicitly built so
that expanding the context window cannot solve it. Scores are meaningfully lower than on
LoCoMo/LongMemEval, which is the point — it is a benchmark nobody saturates.

*Use it for:* stress-testing architectures intended for years of history.

### DMR (Deep Memory Retrieval)

Established by the MemGPT team as their primary metric; still cited in comparisons (Zep's paper
reports 94.8% vs MemGPT's 93.4% on it). Largely superseded by the above but you will see it in older
literature.

### Newer entrants worth watching

The benchmark space is expanding into the gaps: consistency and hallucination in memory (HaluMem),
project-oriented long-term interaction (RealMem), long-horizon stateful embodied agents (WorldLines),
and framework-native eval suites from the tool vendors. Expect the frontier to keep moving toward
**agentic, tool-using, multi-week** settings, because that is where the current benchmarks are
weakest.

## 8.3 Why public benchmarks are not enough

Read reported scores with these five caveats. Published leaderboard numbers on the same benchmark
vary enormously across sources — different actor models, different retrieval configurations,
different judging prompts — so cross-source comparisons are frequently apples-to-oranges.

1. **Different actor models.** A memory system evaluated with a frontier model looks better than the
   same system with a small one. The number measures the *pair*, not the memory layer.
2. **Judge variance.** Most are LLM-judged. Different judge models and prompts move scores by several
   points. Always report the judge.
3. **They do not measure cost.** See 8.1.
4. **They do not measure the write path in isolation.** A system can score well by storing everything
   verbatim and retrieving hard — great on the benchmark, unaffordable in production.
5. **They do not test what production breaks on:** poisoning resistance, deletion correctness,
   cross-tenant isolation, staleness, cold start, or user-perceived creepiness.

**Conclusion:** use public benchmarks for architecture selection and sanity-checking. Use your own
harness for everything else.

## 8.4 Building your own eval harness

Four layers. Build them in this order; each is cheap and catches different bugs.

### Layer 1 — Unit tests on the write path

The scenario suite from chapter 04.10. Fast, deterministic-ish, runs in CI on every change. This is
your regression gate.

```python
def test_supersession():
    mem = fresh_store()
    mem.ingest("I live in Pune", ts="2025-01-01")
    mem.ingest("I moved to Mumbai last month", ts="2026-03-01")
    current = mem.query_current(subject="user", predicate="lives_in")
    assert current.object == "Mumbai"
    historical = mem.query_at(subject="user", predicate="lives_in", t="2025-06-01")
    assert historical.object == "Pune"
```

### Layer 2 — Retrieval metrics on labelled data

Recall@k, nDCG@k, MRR from chapter 03.9. Fast, no LLM needed at eval time, and it isolates retrieval
from generation. When end-to-end quality drops, this tells you immediately whether retrieval is the
cause.

### Layer 3 — End-to-end QA on your own conversations

The real test. Build it from your own traffic:

```python
@dataclass
class MemoryEvalCase:
    setup_sessions: list[Session]     # history that must be ingested first
    query: str                        # the question, in a NEW session
    expected: str                     # gold answer
    category: str                     # recall|update|temporal|multi_hop|abstention|preference
    must_not_contain: list[str]       # privacy / stale-fact assertions
```

Two properties are non-negotiable:

- **The query must be in a new session**, so session memory cannot answer it. Otherwise you are
  testing your context window, not your memory.
- **Include abstention cases** (~15% of the set). Ask about things never mentioned; the correct
  answer is an admission of not knowing. If you build only positive cases, you will optimise your
  system into a confident confabulator, and you will not find out until users do.

Also include `must_not_contain` assertions — e.g. after a user says "forget my old address", assert
the old address appears in no answer. This is how you test deletion behaviourally rather than just
at the storage layer.

### Layer 4 — Online metrics

The ground truth. Offline evals correlate imperfectly with user experience; these do not.

- **User correction rate** — how often users say "no, that's wrong". Best single proxy for memory
  quality.
- **Memory citation/usage rate** — chapter 07.9. Low usage = wasted tokens.
- **Explicit feedback** on memory items, if your UI exposes them (it should).
- **Deletion rate** — users deleting memories signals either creepiness or errors. Segment by
  category to find out which.
- **Session-over-session task success** — the actual business metric. Does having memory make users
  succeed more?

## 8.5 Test design: the categories that matter

Structure your eval set by ability, not by topic, so failures are diagnostic. Minimum viable
distribution:

| Category | % | What it tests | Typical failure |
|---|---|---|---|
| Simple recall | 20% | Single fact from one past session | Retrieval miss |
| Multi-session synthesis | 15% | Combine facts across sessions | Fusion / k too small |
| Knowledge update | 20% | Superseded facts | Write path — no supersession logic |
| Temporal reasoning | 15% | "What was true when", durations, ordering | No bi-temporal model |
| Abstention | 15% | Never-stated facts | Overconfident generation |
| Preference application | 10% | Implicit use of stored preferences | Retrieval gate / query construction |
| Negative/deletion | 5% | Deleted facts must not surface | Incomplete deletion cascade |

**Weight knowledge update and abstention heavily.** They are where real systems fail and where public
benchmarks (LoCoMo especially) under-test. If your eval set is 80% simple recall, you will ship a
system that is great at simple recall and embarrassing at everything users actually notice.

## 8.6 The judge

Most end-to-end grading is LLM-based. Getting the judge right matters more than people assume.

```python
JUDGE = """Compare the system's answer to the gold answer.

Question: {question}
Gold answer: {gold}
System answer: {answer}

Grade CORRECT if the system answer conveys the gold information, even if worded differently
or with extra context. Grade INCORRECT if it contradicts the gold, omits the key fact,
or is unhelpfully vague.

For abstention questions (gold = "not stated"), grade CORRECT only if the system explicitly
indicates it doesn't have that information. A plausible invented answer is INCORRECT.

Return JSON: {{"grade": "CORRECT|INCORRECT", "reason": "one sentence"}}
"""
```

Discipline that keeps judges honest:

- **Calibrate against humans.** Hand-grade 100 cases; measure judge/human agreement. Below ~90%,
  fix the rubric — usually by adding explicit rules for the disagreement cases.
- **Use a different model family than the actor** where possible, to reduce self-preference bias.
- **Fix the judge version** and record it with every result. A judge upgrade changes your history;
  re-run the baseline when you change judges.
- **Randomise answer position** in any pairwise comparison; position bias is real and large.
- **Log reasons** and read the incorrect ones weekly. Judge failures cluster and are informative.

## 8.7 A/B testing memory in production

Memory A/B tests have three traps that make naive experiments misleading.

**Trap 1: Memory effects are delayed.** A user's first session has no memory to use. Benefits appear
in sessions 3–20. A two-week experiment on a weekly-active product is measuring nothing.
*Fix:* run long, and analyse by session index, not by user-day.

**Trap 2: Novelty and creepiness both distort early data.** Users react to being remembered — some
delight, some discomfort. Both fade.
*Fix:* discard the first week; look at week 3+ for steady-state.

**Trap 3: Averages hide harm.** Memory can help 90% of users slightly and harm 10% badly (a wrong or
embarrassing memory).
*Fix:* look at the *tail* — p5 of satisfaction, complaint rate, deletion rate — not just the mean. A
memory feature that improves the mean and doubles the complaint rate is not a win.

Metrics I would gate a launch on:

```
PRIMARY:   task success rate (sessions 3+)
GUARDRAIL: user correction rate         must not increase
GUARDRAIL: memory deletion rate         must not increase
GUARDRAIL: p95 latency                  must not increase > 50ms
GUARDRAIL: complaint / thumbs-down rate must not increase
SECONDARY: tokens per turn, session length, return rate
```

## 8.8 Regression gates in CI

What actually runs on every PR:

```yaml
memory_ci:
  fast (every PR, < 3 min):
    - write-path scenario suite            # ch 04.10, must be 100%
    - cross-tenant isolation test          # must be 100%
    - retrieval recall@20 on 200 labelled queries   # must not drop > 2% vs baseline
    - compaction identifier-preservation   # must not drop
    - deletion cascade test                # must be 100%

  nightly (< 45 min):
    - end-to-end eval, 500 cases, all categories
    - token cost per query (must not increase > 10%)
    - latency benchmark p50/p95/p99
    - LoCoMo subset (200 q) for external comparability

  weekly:
    - full LongMemEval_S
    - poisoning red-team suite (ch 09)
    - counterfactual memory-usage ablation
```

The **must-be-100%** items are the ones where a single failure is a bug, not a metric regression:
isolation, deletion, and the write-path scenarios. Do not let those become "we're at 97% and
trending up".

## 8.9 Comparing architectures fairly

If you are choosing between memory architectures — build vs. Mem0 vs. Zep vs. LangGraph store —
here is the harness that makes the comparison honest:

1. **Fix the actor model and the judge.** Same for all arms.
2. **Fix the eval set** — ideally your own data, plus one public benchmark for external
   comparability.
3. **Measure the triple** for each arm: accuracy, tokens/query, p95 latency.
4. **Measure the write cost too** — tokens and dollars per session ingested. Graph-based systems can
   be an order of magnitude more expensive to write, which never appears in accuracy tables.
5. **Run the operational tests:** deletion correctness, tenant isolation, restore from backup,
   behaviour on a 100k-memory tenant.
6. **Score the non-functionals:** licence, self-host support, data export, governance model,
   dependency risk. Vendors in this space have changed licences, retired community editions, and
   moved features behind hosted platforms with little notice — a memory layer is a deep dependency
   and a migration is expensive, so weight this heavily.

Write the result up as a table with all six dimensions. A decision made on accuracy alone will be
revisited within a year.

## 8.10 Exercises

1. Build the Layer-3 harness with 100 cases from your own history, including 15 abstention cases.
   Measure your current system. The abstention number will be your worst; that is normal and it is
   the most actionable finding you will get.
2. Calibrate an LLM judge against your own hand-grading on 100 cases. Report agreement. Iterate on
   the rubric until you exceed 90%.
3. Run your system on a LoCoMo subset. Compare to published numbers, then list every reason your
   number is not comparable to theirs. The list will be long; that is the lesson.
4. Design the A/B test for adding memory to an existing product. Write the metric definitions,
   guardrails, the analysis plan by session index, and the stopping rule — before looking at any
   data.
